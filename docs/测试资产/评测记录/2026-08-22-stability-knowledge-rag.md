## 知识库真实并发链路

测试链路：分片上传 → 重复分片幂等校验 → 合并 → 重复合并幂等校验 → Outbox → Kafka → 解析/分块 → 批量 Embedding → Elasticsearch → 检索验证。

脚本：`docs/测试资产/执行脚本/当前可用/run-knowledge-concurrency-baseline.ps1`

### 问题复现

参数：12 份文档、每份 16 KiB、每份 4 个分片、并发 12、同一用户。

| 运行 ID | 接受 | READY | HTTP 429 | 上传 P95 | 已接受任务处理 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `20260822-102311` | 5/12 | 5/12 | 7 | 930.49 ms | 10.25 s |

根因：`KnowledgeResourceLimiter.processing()` 和 `embedding()` 已使用公平等待，但 `upload()` 仍使用 `Semaphore.tryAcquire()`；达到单用户并发上限后立即抛出容量异常并返回 HTTP 429。

### 修复与复测

修复：上传许可改为与处理、Embedding 相同的公平等待；线程中断仍保留明确失败，不把正常排队当成任务失败。

相同参数连续复测：

| 运行 ID | 接受 | READY | 拒绝/失败/超时 | 上传 P95 | 处理 P95 | 吞吐 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `20260822-102603` | 12/12 | 12/12 | 0/0/0 | 806.96 ms | 25.15 s | 0.449 docs/s |
| `20260822-102643` | 12/12 | 12/12 | 0/0/0 | 1022.96 ms | 22.18 s | 0.506 docs/s |

结果：成功率由 41.7% 提升到连续两轮 100%，429 从 7 降到 0。处理 P95 变长是因为修复后 12 份文档全部进入队列并完成，不能与修复前仅完成 5 份直接比较。

较轻负载 `20260822-102245`（6 份、8 KiB、并发 6）为 6/6 READY，上传 P95 532.52 ms，处理 P95 6.87 s。

曾使用 `simple-upload` 做过 60 份探测，全部 READY，但该接口不经过前端使用的分片、Outbox、Kafka、Embedding 和 ES 全链路，因此不计入本次异步并发结论。

## ReAct Agent TTFT 与链路优化

任务：读取同一最小 Project 的 `README.md`，用一句话说明项目名称。每个任务实际执行 Project manifest 和文件读取两个工具；使用真实 DeepSeek 路由。当前 SSE 没有 token delta，首个用户可见内容是完整 `delivery`，因此这里的 TTFT 是“首个 delivery/question”，基本等于完整回答时间。

### 优化前问题

核心只读 Project 工具也必须先 `search_tools`、再 `load_tool`，简单任务平均产生 8.33 次模型调用；真正两次工具调用总耗时约 0.1 秒，主要耗时和 token 花在工具发现轮次。

### 优化

仅预加载 `list_project_files` 和 `read_project_file` 两个只读、小 schema 工具。其他注册工具、修改工具和执行工具仍保留 search/load 渐进披露，不增加权限，也不绕过原有工具参数与证据校验。

相同口径（顺序 3 次 + 并发 3 次）前后对比：

| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 成功任务 | 6/6 | 6/6 | 不变 |
| 平均模型调用 | 8.33 | 3.00 | -64.0% |
| 平均总 token | 23,032 | 8,994 | -61.0% |
| Trace 平均任务耗时 | 11.66 s | 4.68 s | -59.9% |
| 顺序首个可见内容 P95 | 14.67 s | 5.04 s | -65.7% |
| 并发 3 首个可见内容 P95 | 13.71 s | 4.96 s | -63.8% |

额外排队测试：优化前同时提交 6 个任务，6/6 均成功；前 3 个约 0.3 秒进入 `running`，后 3 个等待并发许可后运行，没有把资源限制当成任务失败。并发 6 的首个可见内容 P50/P95 为 13.46/20.07 秒。

验证：Agent Engine 测试 53/53、TypeScript typecheck 和 build 全部通过；优化后真实任务 6/6 成功，每个任务固定 3 次模型调用、2 次工具调用、failureCount=0。

## Redis 后续基线

Redis 并非完全未使用：当前 `AgentMessageCacheService` 会缓存最近 50 条可见消息和 turn 状态，TTL 为 6 小时。但 `AgentContextBuilder` 的上下文组装仍会从 MySQL 按会话读取完整历史，长会话加载可能变慢。

下一阶段先测冷缓存/热缓存下的会话历史接口和上下文组装 P50/P95、SQL 次数与返回大小，再决定采用分页、版本化缓存还是摘要快照增强；不在本轮知识库结论中混入 Redis 改动。

## 交互卡顿与 Sandbox 验证修复

根据 2026-08-22 前端实测日志补充三项修复：

- 工作区文献检索在检索规划、各来源检索、候选排序、重排和完成阶段实时推送进度；相同 `clientRequestId` 的 WebSocket 重连/HTTP 回退复用原任务，并提示正在等待，不重复执行检索。
- ReAct SSE 的 Spring MVC 异步超时由默认约 30 秒调整为 20 分钟，并透传禁用代理缓冲的响应头；非终态断流由前端静默按最后事件序号重连，不再显示为任务失败。
- Sandbox 根据已观察到的项目结构给出 Maven、独立源码或文档/配置检查策略；运行前要求检查 import/依赖描述文件。相同 Workspace revision、argv 和输入哈希的成功回执直接复用，避免“运行成功→查看 diff→再运行一次”的重复开销。

补充回归：首次前端复测时模型生成了白名单外命令 `mvn -o compile`，Gateway 返回 `SANDBOX_COMMAND_DENIED`，但该 400 错误被归类为 `sandbox_system` 后未进入 Engine 的参数修复分支。现已增加 Maven 目标的本地预检，并将 `SANDBOX_COMMAND_DENIED` 明确列为可修复策略拒绝；模型会收到只能使用 `test/verify` 的反馈后重试。专项测试 1/1 通过：非法 `compile` 未提交 Gateway，修正后的 `test` 只提交一次。
